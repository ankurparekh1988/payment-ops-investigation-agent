# 0018. Evaluation thresholds from measured run-to-run spread

- **Status:** Accepted
- **Date:** 2026-11-02

## Context

[ADR 0012](0012-evaluation-thresholds-from-a-pre-registered-rule.md) set each threshold one item below the worst of three baseline runs: `floor_to_0.01(min_b − 1/N)`, gated on the median of three runs. That allows one item of variation. The agent varies by much more.

Across 21 runs of an unchanged agent, from #42 to #49 (same prompt, model, tools, knowledge and data), the per-run counts were:

| Metric | N | Range | Mean | SD | Baseline runs | Threshold needs | Runs below it |
|---|---|---|---|---|---|---|---|
| `tool_argument_accuracy` | 54 | 30–39 | 34.5 | 2.6 | 35, 36, 36 | 34 | 33% |
| `required_tool_recall` | 86 | 66–71 | 68.8 | 1.8 | 68, 68, 70 | 67 | 14% |
| `expected_evidence_coverage` | 66 | 41–50 | 47.8 | 2.1 | 47, 49, 49 | 46 | 10% |
| `validated_result_rate` | 37 | 33–37 | 35.7 | 1.0 | 35, 35, 36 | 34 | 5% |
| `allowed_outcome_rate` | 37 | 30–35 | 33.3 | 1.4 | 32, 34, 34 | 31 | 5% |

With those per-run rates, a median of three fails an unchanged agent in roughly one evaluation in three, mostly on tool argument accuracy. That's what happened: of seven evaluations from #42 to #49, three failed (#44 twice, #49 once) with no change to what the agent is given. Three baseline runs that happened to land high on tool arguments set a line through the middle of the agent's normal spread. Some runs in that period also lost cases to the question screen being throttled, which [ADR 0017](0017-ask-again-when-the-question-screen-cant-check.md) and the `screen` deployment address; they add to the spread but don't explain it.

A gate that fails one change in three by chance trains people to rerun until it passes, which is worse than a looser gate that's believed. It already happened once without anyone choosing it: #44's rerun failed and stood under [ADR 0016](0016-one-recorded-rerun-when-the-agent-is-unchanged.md), then bringing the branch up to date with `main` started a third evaluation of the same agent, which passed and merged.

## Decision

**Thresholds are set from the measured spread of a larger baseline, so that an unchanged agent fails a metric about once in a hundred evaluations. The gate still compares the median of three runs.**

- **The baseline is ten runs** of `main`'s agent at one commit, run like the [ADR 0012](0012-evaluation-thresholds-from-a-pre-registered-rule.md) baseline. For each metric it gives the mean `μ` and sample standard deviation `s` of the per-run counts.
- **The rule, frozen now, before the baseline runs:**
  - higher is better: `floor_to_0.01((μ − m) / N)`;
  - lower is better: `ceil_to_0.01((μ + m) / N)`;
  - where `m = max(1.6 × s, 1)`, in items; then clamped to [0, 1].

  The median of three runs varies about two thirds as much as one run (0.67 × `s`), and 1.6 × `s` is 2.33 of those: about a 1% chance that an unchanged agent's median falls past the threshold on any one metric. The one-item minimum keeps the ADR 0012 tolerance for a metric that didn't vary in the baseline.
- **Hard gates and viability don't change.** Every run must still pass them.
- **`eval/thresholds.json` records `μ`, `s` and the ten per-run values** beside each threshold, and is still generated by the `thresholds` command and never edited by hand.
- **A branch update doesn't buy another evaluation.** An evaluation that follows a failed one on the same pull request, after the branch is brought up to date, is that pull request's one [ADR 0016](0016-one-recorded-rerun-when-the-agent-is-unchanged.md) rerun, and is allowed only where that ADR allows a rerun. It's a new evaluation only if, since the failure, the pull request changed what the agent is given, or `main` changed the agent under test or the gate (the thresholds, labels or rule). Otherwise a failure stands whatever a later evaluation shows, and is recorded.
- **No constant here is changed after the baseline runs.** If the baseline shows a threshold the team doesn't like, that's a finding about the agent or the dataset, handled by its own change and a new ADR.

## Consequences

- With eight gated metrics at about 1% each, an unchanged agent should fail fewer than one evaluation in ten, instead of one in three. [ADR 0016](0016-one-recorded-rerun-when-the-agent-is-unchanged.md)'s rerun stays for that remainder.
- The gate gets less sensitive where the agent is noisy, and that is stated rather than hidden. Half the time it catches a sustained drop of about 1.6 × `s` in a metric's mean, and nine times in ten one of about 2.5 × `s`. On today's spread that's about 4 and 7 tool-argument labels of 54. The degraded prompt in #33 lowered tool argument accuracy to a median of 33, inside the noise, and would likely pass on that metric. It also lowered validated results to 33 of 37, which is past the line on today's spread, where `validated_result_rate` would need 34.
- Thresholds move both ways. On today's spread, tool argument accuracy would fall from 0.62 to about 0.56, while validated results, allowed outcomes and section precision would tighten. The real values come only from the new baseline.
- Ten runs at about eight minutes each take under an hour and a half, once per baseline. Each pull request still runs three.
- Ten runs estimate `s` to within about a quarter. A baseline that underestimates it gives a gate that's still too tight; the per-run values are kept so a later ADR can pool them with more evidence.
- Pending pull requests are evaluated under whatever thresholds are on `main` when their branch is next updated: a changed gate is the decision a failed change waits for, so that evaluation is new, not a rerun. Nothing here singles one out.
- Merging needs a passing check, so a failure that stands is enforced by review: the record says it stands, and the pull request isn't merged on a later evaluation of the same agent under the same gate.
- The safety evaluation ([ADR 0014](0014-safety-evaluation-from-a-pre-registered-rule.md)) and retrieval thresholds keep their own rules.

## Alternatives considered

- **Five runs per evaluation instead of three.** The median of five varies about a fifth less, so the threshold could sit closer to the mean. Every evaluation would take two thirds longer, and evaluations already take 25 to 30 minutes. A smaller gain than the margin, at a recurring cost.
- **Keep the rule and take a new three-run baseline.** It would fail as often, or more, depending on where three runs land; it doesn't address the cause.
- **Drop tool argument accuracy from the gate.** It's the noisiest metric, but it's the only one that checks the agent asks the tools the right questions. Measured with a wider margin, it still catches a large regression.
- **Compare each pull request with `main` in the same window.** It removes drift between days, but doubles every evaluation's cost and time.
