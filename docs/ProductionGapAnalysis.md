# Production gap analysis

What a production deployment would need beyond this repository, why each item isn't built here, and what would trigger building it. The list grows as the system does.

| Area | Here | In production | Why it's deferred | Trigger to build it |
|---|---|---|---|---|
| Network isolation | Public endpoints, Entra ID and TLS | Private endpoints for Foundry, Storage and Search; App Service VNet integration; public access disabled | Adds cost and networking setup without changing how the AI system behaves | Any real data, or a security policy requiring it |
| App hosting tier | F1: no SLA, no always-on, CPU quota | B1 or higher, multiple instances, deployment slots | A demo workload doesn't need it | Real users or an availability target |
| Search tier | Free: no SLA, 50 MB, and an idle service may be deleted (the next deployment recreates it) | Basic or Standard, with an SLA and replicas | Free holds the knowledge corpus with room to spare, at no cost | Production traffic, or an availability target |
| Environments | `dev` only; one Foundry resource | Separate subscriptions or resource groups per environment, each with its own Foundry resource and state | Doubles cost for no new evidence; the code is already environment-aware | A second team or a production rollout |
| Region resilience | Single region | Secondary region with a tested failover | Global Standard model deployments already route across regions | A recovery-time objective that one region can't meet |
| Systems of record | One synthetic dataset built into the app, read in memory | Adapters over the real merchant, payments, payout, processor and log systems, with paging, freshness and their own failure handling | The agent's behaviour is what's being built; the data ports and their contract tests are what a real adapter has to satisfy | Any real data source |
| Payment lookup | No tool finds a payment by its id alone; a question naming only a payment relies on the demo ids carrying the merchant's (`PAY-6230-04`) | A payment lookup tool over the payments system, so a question naming a payment id, card reference or processor reference reaches the right merchant | Every seeded question names the merchant or a payment id that carries it | A real payments system, whose ids don't carry the merchant |
| Investigation history | A conversation per open page, in memory: lost on refresh, sign-out or restart | Conversations kept durably per user, resumable and auditable | One person investigating in one sitting doesn't need them kept | Investigations that must survive a restart, or be handed over |
| Incident tickets | An in-memory store behind a domain port, capped at 1,000 tickets and lost on restart; a ticket is visible only on its owner's card | A real ticket system (the processor's portal or an internal one) behind the same port, with its own idempotency | No ticket system exists here; the port and its contract tests are what an adapter has to meet | Any real incident process |
| Approvals | Pending proposals in one process's memory, expiring after 15 minutes; lost on restart, deploy or slot swap | Durable, shared approval state with an audit trail, surviving restarts and shared across instances | One instance and short-lived proposals don't need it | More than one instance, or approvals that must outlive a session |
| Scale-out | One instance: the gate, conversations and proposals live in that process | Shared state and per-user affinity, or stateless services over a shared store | The demo runs one instance | A second instance or an availability target |
| Ticket list | None: a ticket is seen only on the card that created it | A list of tickets and their status, with search | Nothing here reads tickets after creation | Anyone needing to follow up on tickets |
| Ticket severity | Not proposed or recorded | A severity the approver sets or confirms, driving routing | Severity needs an agreed scale and routing that don't exist here | A real incident process |
| Groundedness detection | Statements are validated against the ids they cite, not against what the cited text says | A groundedness check of each statement against its cited sources | Not offered for this region; citation validation already rejects unsupported ids | Availability in the region, or answers found citing real sources for things they don't say |
| Counterfactual fairness | Not tested | Paired cases that differ only in merchant attributes, checked for different answers | The agent decides nothing about merchants and the data is synthetic | The agent informing any decision about a merchant |
| Content Safety processing location | Prompt Shields is called on the Canada Central Foundry account, but where the operation is processed isn't documented for the region | Confirmed in-region processing, or a region where it's documented | Synthetic data | Real data with residency requirements |
| Bank-detail DLP | Ticket text is checked for card-like numbers, runs of eight or more digits and IBAN-shaped tokens, by rule id only | A managed data-loss-prevention policy for bank details and personal data across every outbound channel | Synthetic data, one outbound channel and a conservative rule are enough here | Real customer data, or tickets leaving the organisation |
| Agent evaluation runs | Pull requests that change AI behaviour or gate policy are evaluated in CI as an identity that can only call the model and read the indexes, after a maintainer labels it for evaluation and approves the environment; `main` is evaluated monthly while that run is switched on, and recorded in Log Analytics. GitHub disables a public repository's scheduled workflows after 60 days without activity | Evaluation on a scheduler that doesn't depend on repository activity, alerting through the operations on-call route, and approvals by someone other than the author | One maintainer, the monthly run is a monitor rather than a release step, and every run is paid for by the call | A second maintainer, an operations alert route and an evaluation budget |
| Safety thresholds | The safety evaluation's hard gates fail the check; its six detection and false-positive rates are reported, not gated, and a pull request runs it once | Thresholds frozen from a baseline of `main` by the rule already written in [ADR 0014](adr/0014-safety-evaluation-from-a-pre-registered-rule.md), and several runs per change | The ten-run baseline costs about three evaluations, for rates no change here has moved ([ADR 0020](adr/0020-evaluate-on-request-at-lower-cost.md)) | Budget for the baseline |
| Model routing | A cascade from a small model to chat, built and off, turned on only by a pre-registered measurement over 37 cases × 3 runs; measured once and rejected ([ADR 0023](adr/0023-route-to-a-small-model-first-by-a-pre-registered-rule.md)) | Routing measured on production-like traffic, re-measured for every model version, with a running comparison of escalation rate and answer quality | The labelled cases are the only traffic here, and one measurement is all they can support | Real traffic, or a model version change |
| Per-user limits | One investigation at a time per open page, 20 questions per conversation, a token cap per model call, and daily limits per person and in total, held in a table ([ADR 0021](adr/0021-bounded-usage-and-observable-cost.md)) | Per-minute rate limits and token budgets per user | Daily limits bound a demo's use; bursts within a day don't matter at this scale | Shared use with an availability target, or bursts that crowd others out |
| Spending control | Budget alerts and a cost anomaly alert by email; a pause switch; daily limits; per-investigation usage and estimated cost; a budget-driven cutoff, built and off ([ADR 0021](adr/0021-bounded-usage-and-observable-cost.md)) | Alerts routed to on-call; spending limits enforced by the billing account | One person runs the system and watches the alerts | Shared or unattended use |
| Human access | The owner holds standing Owner rights; scripts refuse local applies, but that's a guardrail rather than a control | No standing write access: just-in-time elevation (Privileged Identity Management) for break-glass only, enforced by Azure Policy | One person operates the system | More than one operator, or a compliance requirement |
| Encryption keys | Microsoft-managed keys | Customer-managed keys in Key Vault for storage and Foundry | Synthetic data doesn't justify key management | Real customer data or a regulatory requirement |
| Storage audit logs | Entra-only, role-scoped access; no data-plane logs | Blob read/write diagnostic logs to Log Analytics for the state and knowledge containers | Adds ingestion cost for little signal at this scale | Real data, or any need to audit who read the corpus or state |
| Review of AI changes | Pull requests to `main` require passing CI checks; there's one maintainer, so no independent approval | Code-owner approval required for `ai/**`, from someone other than the author | An author can't independently approve their own change | A second maintainer |
| Evaluation history view | Evaluation results are rows in Log Analytics (`AiEvaluation_CL`), read with a query | A workbook of verdicts and metric trends per release, beside the operations workbook | A query answers the few questions one maintainer asks of it | Anyone other than the maintainer reading evaluation history |
| Capacity view | The operations workbook shows model tokens per day by deployment and throttled calls; deployment capacity is in the AI release manifest, not in Log Analytics | A chart of tokens per minute against each deployment's capacity, with an alert before throttling | Throttling is already alerted on, and demo traffic is far below capacity | Sustained traffic, or throttling alerts |
| Telemetry volume | Daily ingestion cap | Sized retention, archive to storage | The cap keeps cost bounded; dropped data is acceptable here | Audit or retention requirements |
